LEGENDARY PROGRESSION — V2.4
ACCOUNTS, AUTHENTICATION & USER DATA SEPARATION

V2.3 is complete and stable.

V2.4 turns Legendary Progression from a development/profile-based application into a secure multi-user application.

IMPORTANT:
- Do NOT rewrite the V2.3 progression engine.
- Preserve all V2.3A/B/C functionality and tests.
- Do NOT reset/drop PostgreSQL.
- Do NOT delete existing workout history.
- Use safe migrations.
- Authentication and authorization must be enforced SERVER-SIDE.
- Do not build a fake frontend-only login system.
- Do not store plaintext passwords.
- Use established secure authentication/session practices.
- Preserve the current mobile/PWA-first experience.
- The attached gold Legendary Progression dragon artwork is the official authentication/welcome-screen artwork.

==================================================
1. ACCOUNT MODEL
==================================================

Move toward:

ONE ACCOUNT = ONE ATHLETE

A logged-in account owns its own:

- settings/preferences
- mesocycles
- training splits
- planned workouts
- completed workouts
- completed sets
- exercise baselines
- prescriptions
- PR/history
- recovery/readiness information
- post-exercise feedback
- Total Weight Lifted history
- Calendar data

The current development profile-selection system must NOT remain the security boundary.

Authenticated account identity becomes the security boundary.

Do not allow one account to access another account's training data.

==================================================
2. PRESERVE EXISTING USER DATA
==================================================

CRITICAL:

Existing V2.3 data must not be lost during authentication migration.

Do not automatically delete, recreate, or detach existing profiles.

Create a safe migration strategy that allows the current primary working profile/data to become associated with an authenticated account.

Before modifying ownership relationships:

- inspect current user/profile relationships
- inspect foreign keys
- identify records belonging to existing profiles
- determine a safe account/profile migration
- preserve completed history

If ownership is ambiguous, STOP and report the ambiguity rather than assigning historical data to the wrong account.

Do not reset the database as part of authentication implementation.

==================================================
9. SERVER-SIDE AUTHORIZATION
==================================================

This is CRITICAL.

Authentication answers:

"Who is this user?"

Authorization must answer:

"Does this user own this requested resource?"

Every protected server/API operation must derive or verify ownership from the authenticated account.

Do not trust arbitrary client-provided user/profile IDs.

Example:

Authenticated Account A requests workout 500.

Server must verify workout 500 belongs to Account A.

If it belongs to Account B:

DENY ACCESS.

Changing an ID in a request must never expose another user's data.

==================================================
11. SHARED VS USER-OWNED DATA
==================================================

Clearly distinguish GLOBAL/shared application data from USER-owned data.

GLOBAL examples:

- standard exercise library
- Legendary template definitions
- general application configuration

USER OWNED examples:

- custom exercises created by that user
- mesocycles
- workouts
- sets
- PRs
- baselines
- feedback
- recovery
- preferences

A user may read shared exercise/template data.

A user must not modify global records in a way that affects every other user unless specifically intended/admin-controlled.
